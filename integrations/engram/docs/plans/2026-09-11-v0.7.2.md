# dsh-engram v0.7.2 Implementation Plan (True Memory Palace: Slots + Spaced Repetition + Fixed Tour + Nameplate Rules)

Motivation: The palace elements in v0.7.x (imagery nameplates, corridor graph, dynamic tour) only exist in the narrative/display layer; the recall and reinforcement paths (importance-sorted injection, RRF search, hit +0.05) have nothing to do with palace logic. This version lands the memory palace's **information architecture** into the kernel — the palace's value to AI is four things: use position as an index, use fixed routes to define order, let the skeleton be reused long-term, let every marker be unique; the sensory/emotional dimension is a human-brain patch, AI doesn't need it, not counted into the quality score.

Architecture alignment (user's diagram "directory is room, path is route"):
- **Main Hall · resident core memories** = profile injection (top N present every round), rendering annotated "Main Hall resident".
- **Corridor · routing index** = engram_search's room parameter + engram_stats's room directory: first decide which room to enter, then search within the room, not scanning the whole database right away.
- **Rooms** = kind-based rooming (Fact Hall / Preference Pavilion / Decision Hall / Episode Gallery / Skill Workshop) + capacity expansion; scope-based database corresponds to the "per-person / per-project" palace group.
- **Nameplate rules** = unique · differentiated · with date; prohibit two memories being so similar they can't be distinguished (save-time instant scoring + hint, refurb fallback).

## Key Design Decisions (Locked In Before Implementation)

1. **schema v6 adds six columns one table** (all nullable/with defaults, zero data migration):
   - `slot_room TEXT` / `slot_index INTEGER`: slot (room + in-room sequence number); NULL = un-slotted (existing entries slotted in one batch by backfill).
   - `imagery_score REAL`: imagery quality score (heuristically computed and stored at save time, data source for refurb low-score rule).
   - `next_review_at INTEGER` / `ease_factor REAL` / `interval_days REAL`: SM-2 scheduling state; NULL = not entered review scheduling (existing entries not scheduled, keeps old decay behavior).
   - `CREATE TABLE tour_routes (position INTEGER PRIMARY KEY, node_id TEXT NOT NULL)`: fixed tour route (one per database, append-only; when an entry is archived/forgotten, tour rendering skips it, does not delete the position — the palace's slot does not collapse because one item is removed).
2. **SM-2 simplified (src/review/sm2.ts)**: grade 0-5; ≥3 passes, interval 1 → 6 → round(prev × ease); <3 resets interval to 1 day, reps cleared; ease floor 1.3. Signal source: `engram_report` (success=5 / failure=1, new optional `grade` parameter explicit self-assessment takes priority). At save time new entry initial schedule `next_review_at = now + 1 day` (`reviewScheduling: false` disables).
3. **decay linkage**: entries entered into review scheduling (next_review_at IS NOT NULL) do not participate in automatic decay — a memory due for review not yet reviewed should be reviewed with priority rather than archived; its exit is taken over by the refurb checklist demote rule (manual confirmation).
4. **Slotting rules**: default room by kind mapping (fact→Fact Hall / preference→Preference Pavilion / decision→Decision Hall / episode→Episode Gallery / skill→Skill Workshop), room capacity 9 (7±2 cap), full auto-opens `<room name>-2` and records op_log. Existing backfill: room by kind, created_at for order, idempotent (only processes slot_room IS NULL).
5. **engram_tour dual mode**: `mode: 'thematic'` (status quo, query-driven dynamic route) / `'fixed'` (walks the whole palace in tour_routes table order, reports slot per stop). Auto-append route at save time.
6. **Search practice closed loop (agent side)**: new tool `engram_review_queue` returns today's due queue — only gives clues (room + slot + imagery nameplate caption), **not content**; the model first tries to recall, then uses `engram_review` to reveal and check, `engram_report grade` to self-assess. Profile injection and profile rows carry slot numbers (`<room name> #<sequence>`), if there are due entries at the first round of the session, append a line "N segments to recall today" at the end of injection.
7. **Nameplate rules (src/imagery/score.ts)**: 0-1 heuristic — caption valid (4-30 chars) and unique across the database +0.4, with date/time anchor (YYYY-MM-DD or "X year X month" etc.) +0.3, differentiated from other nameplates in the same room (first 6 chars do not repeat existing captions) +0.3. Sensory fixation and emotion weights are **not scored** (human-brain patch, AI doesn't need it), fields retained for compatibility. When < 0.5, engram_save output attaches an enhancement suggestion, refurb adds a low-nameplate rule.
8. **Encoding-specific cues**: search top5 hits attach the same room's adjacent slot (slot ± 1) id list; tool output and profile rows carry "engraved on <date> · <room name> #<slot>".
9. **Routing index**: engram_search adds optional `room` parameter (in-room search; default whole database keeps compatibility); engram_stats outputs the room directory (room name/slot count/nearest nameplate) as the basis for "first decide which room to enter"; profile injection rendering annotated "Main Hall resident".
10. **Panel**: new "Today to Recall" card (GET /api/engram/review-due; reveal → self-assess remembered/fuzzy/forgot → POST review-answer); palace display list adds "by tour route" sort switch.

## Verified Code Facts

- decay SQL: sqlite.ts:310 `sqlDecay`, add `AND next_review_at IS NULL` condition.

**Deviations from plan**: Decision 5's "tour-proposal reads fixed route" was not implemented — `engram_tour mode=fixed` already covers fixed-route touring, palace navigation still sorts by importance×confidence. Decision 7's "engraved on <date>" lands in `engram_search` hit rows; profile injection rows and `engram_stats` room directory only carry "room#slot" coordinates, no date anchor (date in profile rows is a resident cost, insufficient benefit). Both are non-blocking, left for later versions as needed.

**Defect found by empirical run (fixed)**: Running through an agent's real call sequence (save → stats → search room → tour fixed → review_queue → report grade) with the tool executor exposed — `engram_save` single-entry path returned an object that **dropped the `text` field** when there was no nameplate hint, the model only saw `{id, kind, importance}`, could not see the just-created slot coordinates; the batch path's `items` also did not include slots. Both places changed to always return hint text with coordinates (batch `items` adds a `slot` field and syncs output schema and summary text), and assertions were added. (The temporary empirical script was deleted after running, not committed.)

**Migration regression (user on-site error `no such column: slot_room`, fixed)**: v6's two index-creation statements (`nodes_slot` / `nodes_review_due`) were once placed in the table-creation exec **before the migration**; a new database's table already contains v6 columns so no problem, but when any old database is opened the columns do not yet exist, exec directly throws — the migration never had a chance to run, the database stopped in a half-migrated state (`tour_routes` created, columns not added, version number still 5). Fix: move the two indexes out of the front-exec, supplement creation in the new-database branch, old database has `MIGRATIONS['5']` create them together with the column additions. The original migration test simulated an old database by "create at current version then downgrade version number", the columns actually already existed, so it was missed; a **real v5 structure** (hand-written SQL, no v6 columns) migration test covering this path was added, and it was verified that after migration new writes can slot normally and indexes are in place. The user's 6 real databases (including two v2 old ones, going through the full v2→v6 chain) have been verified in-place migration passed: version 6, 7/7 columns, existing entries back-filled with slots and registered on tour routes.

**Issue #1 (process fatal exit when session is disposed)**: The reporter gave the complete stack and root cause, after re-checking it was confirmed the current code still has this defect. Chain: the `session/disposed` observer is fire-and-forget and **has no `.catch()`** → `ingestFinalTurn` calls `lastTurnNumber(deps.events)` **outside** the try → after dispose the event source is detached making events undefined → `turnStarts` reads `events.length` throwing TypeError → the async function returns a rejected promise no one handles → host `installFailLoud` treats it as a fatal error `process.exit(1)` (the same defect in the preStep path only downgrades to a warning because it has `.catch()`, hence the "suddenly exit after repeated warnings" behavior). Three-layer defense-in-depth fix: ① `turnStarts` treats undefined as an empty log; ② `ingestFinalTurn` moves the round-number fetching into the try, making that function **never reject** (when the round number cannot be fetched, do not land a pending — the key needs a round number, only skip); ③ the dispose call site adds a `.catch()` fallback. Two regression tests: unit layer covers undefined event source not throwing, composition layer uses real Loader + `snapshotEvents: () => undefined` asserting no unhandled rejection is produced. The test validity was verified — temporarily reverting the three-layer fix made the composition test reproduce the exact same stack as the issue and it was recorded by vitest as `Errors 1`, after restoring all green.
