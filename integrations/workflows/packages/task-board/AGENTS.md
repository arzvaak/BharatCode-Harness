# AGENTS.md — dsh-task-board

The Host-authoritative, multi-column task board for the dsh Web GUI. Tasks run in real DSH sessions; the browser only displays state asynchronously and submits actions.

## Host Ledger, Execution, and Scheduling

- The authoritative ledger is `$DSH_HOME/task-board/ledger-v2.json` (the filename is retained for historical reasons), with the current schema `{ schemaVersion: 4, revision, tasks, scheduler }`. On Host startup, legacy v2/v3 documents are migrated field by field without data loss and written back as v4 (v4 stamps the Host time zone into `ScheduleRule.timeZone`). Migration failures must report an explicit error and preserve the original file; never silently clear it. Writes must retain the temporary-file-plus-atomic-rename pattern, corrupt-file quarantine, and monotonically increasing revisions.
- Browser storage `dsh.taskBoard.v1` is retained solely for one-time import. Write the import marker only after Host confirmation. All production changes go through the strict same-origin action protocol in `protocol.ts`; the UI must not write unconfirmed state first.
- Manual and cron runs share `HostExecutionRunner`. If any pinned workspace, agent preset, or permission is unavailable, fail closed before the task prompt. By default, each execution creates a separate session. With `reuseSession` enabled, a task may reuse its previous session; `core/session-reuse.ts` is the sole authority for eligibility: the previous execution must be settled, and the session must still be present in the roster and idle (an unknown roster never permits reuse). On reuse, reapply the pinned permission and model before queueing the prompt; do not rename or create a session. `reuseSessionFor` reads the roster for that launch rather than using polling cache, which may be stale once an idle board stops polling.
- Read the session roster only when the board needs it to make a roster-dependent decision (issue #1821): `HostTaskLedger.runtimeView().needsSessionState` is true when an execution needs reconciliation or a card is in the running column (its settlement may have come from a write this process did not observe). Do not poll an empty board with no running cards, unsettled executions, or enabled schedules; the Host must not rebuild persisted session rows. The `sessionPollSeconds` setting (default 5, range 1..300, volatile; `src/core/poll-cadence.ts` is the sole source of its range and conversion) controls polling. If a poll cannot read the roster (throws or returns `known: false`), exponentially back off up to one minute; reset the delay after a successful read. This avoids repeatedly hitting a broken session tree at the normal polling interval. Deliberately do not inspect the extension registry: the provider surface (`TaskBoardExtensionHost`) has no session capabilities, and counting extensions would weaken the fix.
- Goal execution is enabled by default. Unless `goalRun: false` is explicit, the runner queues the prompt and then runs `/goal <combined prompt>` in the same session (`goalObjective` formats the goal text to avoid `/goal`'s own keyword syntax). If `/goal` is rejected or the deployment has no command dispatcher, warn and continue as a normal single-turn execution. While a goal is active, use `inspect` on `session/projections` to determine its state: `active` remains pending; `blocked` fails with the goal's own reason; `complete`, `paused`, or no goal uses normal turn settlement. If the read fails, warn and fall back to turn settlement; a failed read must not leave an execution pending forever.
- At execution time, the handover bundle's tuple overrides ordinary pinned fields. A binding whose effective permission is above the permission baseline requires human confirmation through the `confirm-permission` action (any change rearms confirmation). Manual runs reject unconfirmed cards; cron skips them and advances `nextRunAt`. The baseline comes from `sessionDefaultPermission`; when unset, follow the Host's own default permission preset (the optional `permissionPresets` service's `catalog().defaultPreset`, i.e. the starting permission for new DSH sessions). Read it live for each run so Host setting changes apply without remounting. If the deployment does not provide the service, or its default is not one of the three sandbox modes (for example, the current-session-only `auto` mode), fall back to `read-only`.
- Cron uses each rule's IANA time zone (`ScheduleRule.timeZone`, defaulting to the Host time zone). `core/schedule.ts` parses wall-clock times in the target zone through `Intl.DateTimeFormat`; skip nonexistent daylight-saving times and use the earlier instant for repeated times. Dates and weekdays follow Vixie semantics (OR when both fields are restricted, AND otherwise). The v4 ledger migration stamps the Host time zone onto rules without a stored zone so existing trigger times do not shift when `TZ` changes. Skip all occurrences missed during first Host startup or a long pause. Do not queue or overlap a task that is already running; only advance to its next trigger.
- On restart, continue observing running executions that have a session ID; mark interrupted startup executions without a session ID as cancelled and never resend them automatically. Startup recovery and each session poll first fold runs whose outcome can already be determined: settle team executions according to the Lead, and terminate parent/child chains once all members have settled (idempotently; do not write already-folded runs again). A session history read failure does not mean an execution is still running indefinitely: after the roster confirms the session is idle, fail the execution with a reason if history remains unreadable for the limit (24 polls, about two minutes), preventing a card from staying in the running column forever.
- The Host is the sole authority for subtask depth. The `TaskRecord.parentId` depth limit is controlled by `maxSubtaskDepth` (1..3, default 1). Creation, `set-parent` linking, and import repair share the existence, cycle, and depth checks in `src/core/subtask.ts`; the browser only enables or disables controls based on those results. Running a task starts executions for its entire subtree concurrently in one run group. The parent settles only after its own turn and all direct children settle; failure of any member fails the parent. A task already running cannot enter a new run group (including cron), and running participants cannot be relinked or detached with `set-parent`, because their links may still be the run group's parent pointers. Resolve permissions and models not explicitly set on a subtask through its ancestor chain at launch; inherited permissions also use the human confirmation stamp of the ancestor that supplied them. Never copy permissions onto the child card at creation, which could leave a confirmed high-permission root task after unlinking. Store workspace, mode, and model using the values prefilled for the user.

## Agent Team Execution (Opt-In)

- The task-level `teamRun` switch (off by default, selected on the detail page, disabled when the service is unavailable) changes an execution from one session per member to one Lead session plus one teammate per subtask. The Host gets the live Lead with `ctx.agents.get(leadSessionId)`, calls `ctx.agentTeams.spawnTeammate(lead, { name, description, prompt, context: 'fresh', provider: teamProvider, signal })`, then attaches the teammate session ID to that subtask's execution. Settlement does not rely only on the session monitor: a teammate is a persistent Team member, so its session remains alive after its turn. The board reads its first completed turn even if the roster still reports the session as running. The Lead's outcome governs team execution; once the Lead's outcome is known, settle any members that have not reported an outcome according to it, so one silent teammate cannot leave the chain running forever. Resolve `agentTeams` as an optional service (do not inject it). If unavailable, reject manual execution rather than silently reverting to cascade mode; on the cron path, mark members failed and record the reason.
- In this mode, flatten the subtree into one Team (only the Lead can spawn teammates). Teammate names combine a title slug, a stable four-character tag from the member task ID, and the first eight characters of the run group, ensuring uniqueness within a Team and across executions. A slug alone is not unique: titles written only in Chinese collapse to the same generic prefix, and titles sharing their first English word can collide. Agent Teams rejects duplicate names, so using only the slug and run group would make all but the first teammate in one execution fail to spawn. Team execution always creates a new Lead session; it never reuses an old session. Evaluate a subtask's pinned permission against the Lead session's effective permission: teammates inherit the Lead session's permission and cannot be restricted. A pin at or below that permission is allowed (the member runs with the Lead's permission; the detail page explains that subtask permission pins do not apply in team mode). A higher pin rejects the entire run before startup instead of being silently discarded. Members without their own pins inherit the Lead's binding, including its confirmation stamp, and remain subject to the Lead's confirmation gate.
- Prompts in both modes describe the execution shape, including members, their names/task IDs, and available tools. Cascade mode says it starts N independent sessions concurrently; team mode says this session is the Lead and lists its teammates.

## Agent Tool Surface

- The eight model-visible tools `task_board_list` / `task_board_get` / `task_board_create` / `task_board_update` / `task_board_set_parent` / `task_board_run` / `task_board_manage` / `task_board_schedule` are defined in `src/host/agent-tools.ts` and registered through `ctx.tools.register`. They all call the same `TaskBoardHostService` (ledger actions plus snapshots) rather than duplicating business rules. Fail-closed pins, the permission confirmation gate, subtask depth checks, and locks on running tasks apply through the tool surface as well. `task_board_manage` also has a `settle` action: force-settle an unobservable running card (including its member executions) as cancelled, record the caller in the reason, and return the card to To Do for manual or agent recovery. Moving, archiving, or deleting a running card is rejected; `settle` is its only exit.
- Registration follows the `enabled` master switch and stops when it is off. Resolve the tool registry as an optional service rather than adding it to `inject`; deployments without the registry still mount the board but lack its tools, consistent with optional `llm` support.
- Teardown releases registrations but does not re-register. Cordis marks a fiber UNLOADING before running its disposer, at which point `Fiber.effect` rejects new registrations. Therefore, `setToolsEnabled(false)` does not touch the extension tool registry (only the enable path rebinds it), and `syncTools` treats `INACTIVE_EFFECT` as the Host shutting down rather than reporting it; other rejections are still recorded as errors. A provider's `active` flag gates “board × extension,” not Host lifecycle; do not infer one from the other.
- Deliberately do not provide `confirm-permission`: only a human may confirm bindings above the permission baseline in the UI. The tool surface also does not accept commands, executable paths, or shell text.
- Tool descriptions are English model-facing copy and are not in the locales dictionary. Domain rejections return an `ok: false` value so the model can correct its request.

## External Provider Extension Contract

- The board declares three child slots: `task-board.detail.section` (props `{ task, dispatch }`), `task-board.settings.section` (props `{ dispatch }`), and `task-board.card.decoration` (props `{ task }`). Components declare `children` in the `register` options and consume them with `renderSlot`; internal React context carries them to the detail page, settings card, and task card. Cross-package extensions declare matching keys with `declare module` in their own package and must not value-import the board. The board source must not contain provider names: `src/tool-surface.ts` is a generated copy from `scripts/sync-shared.mjs`; the family tool-section order table registers only the Host plugin's order, while external extensions use their family's `EXTENSION_TOOL_SECTION_ORDER` slot to follow the Host. Thus the copy contains no provider IDs; `grep -rn github packages/dsh-task-board/src` must return 0.
- Host and client each publish a Cordis service named `taskBoard`, with API version constant `TASK_BOARD_API_VERSION = 1`. Providers negotiate using this constant; a version mismatch is visibly rejected without affecting the board's continued operation.
- Providers see only the Host capability surface `tasks.{ list, get, create, patchContent, setStatus, linked }`, `integration.{ read, write }`, `events.{ onStatusChanged, onExecutionSettled, onTaskDeleted }`, `publish`, and `registerTool`; and the client capability surface `dispatch` / `registerVisibility` / `subscribe` / `snapshot`. `HostTaskLedger` is not part of the service surface.
- Payloads are opaque. `TaskRecord.integrations` is `Record<string, unknown>`; validate only that it is a plain JSON object no larger than 64 KiB per entry. The protocol exposes only the generic `{ kind: "extension-action", extensionId, action, taskId?, payload? }`; snapshots expose only `extensions?: Record<string, unknown>`. Do not migrate the ledger schema or make the board core depend on normalization of remote semantics.
- The board enforces its own invariants: `patchContent` reuses `canEditTaskContent` (freeze card content after execution or archiving); `setStatus` uses the existing column and permission gates; event callbacks are isolated with try/catch and must never interrupt execution. Remote-identity indexing belongs to the provider; the board does not provide `findTaskByGitHubIdentity` or `updateTaskIntegrations`.
- The switches have three levels: disabling the loader row (requires restart; strongest) > extension `enabled` (volatile, true by default, immediately and lazily stops polling and writes, unregisters tools, and removes detail sections and badges without clearing data) > the board master switch. Keep an extension's settings section reachable because users reopen it there; only collapse or expand its configuration form. See the full contract in the [Agent Note](../../.agents/notes/implemented/architecture/2026-09-30-task-board-extension-contract.md).

## Power Protection

- `preventIdleSleep` defaults to `false`. When enabled, any running DSH session, enabled cron schedule, or unknown session state is a reason to hold the lock. Release it only after confirming there are no running sessions and no schedules.
- On macOS, allow only `/usr/bin/caffeinate -i -w <pid>`. On Windows, allow only the fixed Windows PowerShell helper resolved from `SystemRoot` with `ES_CONTINUOUS | ES_SYSTEM_REQUIRED`. On Linux, allow only an absolute-path `systemd-inhibit` idle/block lock; do not request sleep, display, or lid-switch inhibitors.
- Helpers must use `shell: false`, fixed arguments, and no PATH lookup; use bounded backoff on failure and clean up when the setting is disabled, the plugin unloads, or the Host exits. Do not change power plans or require administrator privileges. On Linux without systemd-logind and on other platforms, report only `unsupported` or a visible error.

## File Ownership and Tests

- Keep Host protocol, ledger, runner, scheduler orchestration, and power state machine in `src/`; browser transport and UI in `src/client/`; pure cron, task conversion, and subtask depth rules (`src/core/subtask.ts`) in `src/core/`.
- Host features depend only on the official `@deepseek-ai/*` NPM SDK and must not import DSH source. `src/dsh-home.ts` and `src/loopback.ts` are generated copies from `shared/host/` by `scripts/sync-shared.mjs`; do not edit them manually.
- Add corresponding unit tests when changing the ledger, protocol, runner, cron, or power behavior. Run the native helper smoke test only when `DSH_POWER_SMOKE=1` on Windows, macOS, or Linux; explicitly skip its native portion on Linux when no logind system bus is available.
